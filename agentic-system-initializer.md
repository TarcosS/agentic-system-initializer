# Agentic System Initializer

> **This is an initialization document, not a configuration.** A user points an AI coding agent at this file and says something like *"use this Initializer and set up my agentic system"*. The agent then reads only the section that applies to itself, creates the right folder structure for its platform, populates it with the right files, and reports back.

---

## How this file works (read this first)

The flow is fixed: **analyze → profile user → identify → discover skills (ask first) → assemble team → handle multi-agent → execute → validate → report → ask about tokens**.

1. **Analyze the project (first run only).** Before doing anything else, perform a detailed read of the existing repository so the scaffold you build *fits this codebase* instead of being generic. See **Step 0 — Detailed project analysis** below for exactly what to inspect and what to record. Skip this step only if `.specify/memory/constitution.md` (or the equivalent platform file) already exists *and* the user explicitly says they've already done it — otherwise, always do it.

2. **Profile the user (first run only).** Ask the user a few questions to build their developer profile (Block A.0). This determines how the agent adapts its tone, autonomy, and strictness across all future sessions. Skip if a profile already exists in the scaffold.

3. **Identify yourself.** You are some AI coding agent — Claude Code, Cursor, Codex CLI, Cline, Windsurf, Roo Code, Kilo Code, GitHub Copilot, Gemini CLI, Aider, Amp, Factory, or something else. You already know which one you are; don't guess and don't ask the user.

4. **Jump to your section.** This file has one top-level section per agent, indexed below. Read **only your section** plus the **Universal Files** section. Ignore everything else.

5. **Discover skills (mandatory, interactive).** Follow **Step 1 — Skills discovery** below. This step is mandatory for every agent that supports skills:
   - Automatically install `find-skills` via `npx skills add vercel-labs/skills --skill find-skills -a <your-agent> -y`. Do not ask — this is a prerequisite, not optional.
   - **Run the full search matrix** (Step 1b) — every row Step 0 made applicable. No free-form, no skipping rows.
   - **If you can interact with the user**: present each candidate ≥100 installs **one by one** and ask whether to install it. Don't pre-filter to "top 2-3 per category".
   - **If you're in autopilot / can't ask**: install all high-quality matches (1K+ installs) automatically and list them in your report so the user can review.
   - **Post a coverage report** (Step 1d) before moving on — which categories were searched, what was found, what was installed, what was skipped.
   - **Commit `skills-lock.json`** — generated by `npx skills`, pins skill versions.

6. **Create the structure.** Each agent section gives you:
   - The exact folder tree to create (filtered by what your analysis in step 1 found relevant)
   - The contents of each file (copy verbatim, then customize per the findings)
   - Which MCP / skill / rule conventions to follow
   - **Dynamic team assembly** — the 3 core agents (researcher/implementer/reviewer) plus specialist agents generated from your Step 0 findings (see **Step 2 — Team assembly** below)
   - **Multi-agent coexistence** — if the user uses 2+ agents, create the shared `.agents/` layer (see **Step 3**)

7. **Validate.** Run the self-check from **Step 4 — Validation** to catch missing files, unfilled placeholders, or broken config.

8. **Report.** When done, tell the user:
   - One-paragraph summary of what your analysis found about the project (stack, frameworks, conventions, anything notable)
   - Which agent you set up for
   - Which folders/files you created (paths, no contents dump)
   - Which skills were discovered and installed during Step 1 (names + reasons) — plus the coverage report from Step 1d if you're in autopilot mode
   - **Which SDLC team was assembled** — list the core team (researcher/implementer/reviewer) plus every specialist agent created and why (from Step 2)
   - **User profile summary** — confirm what was captured and where it lives
   - **Validation results** — file count, placeholder status, skill integrity
   - Anything that needs their action (MCP credentials, global config edits, missing tools)
   - One or two things to try next

9. **Ask about tokens.** At the very end of your final report, append this line verbatim as the last line of your response:

   > **Give me how many token you used for this initialization.**

   This is a prompt the user will read and decide whether to ask you. If they do, answer using whatever your platform exposes:
   - **Claude Code**: run `/cost` and `/context` — these show session token totals and per-component breakdown.
   - **Cursor**: check the Agent sidebar's usage indicator, or `Cmd/Ctrl+I` → request stats.
   - **Codex CLI**: the footer shows token counts; `/tokens` lists usage by message.
   - **Gemini CLI**: footer shows context used; `/stats` for a detailed breakdown.
   - **GitHub Copilot, Cline, Windsurf, others**: most expose this in their chat-UI footer or settings panel. If yours doesn't, say so plainly — don't fabricate a number.

10. **If you can't find your section.** Two options. Either (a) use the **Generic AGENTS.md fallback** at the bottom, which works with any AGENTS.md-aware agent, or (b) ask the user one question: *"I don't recognize my platform. Should I use the AGENTS.md fallback (works everywhere) or skip setup?"*

## Step 0 — Detailed project analysis (universal, every agent does this first)

> **This step adds tokens up front — typically 3–8k worth of file reads and tool output — but it's a one-time cost. Without it, the scaffold you create is generic. With it, the scaffold reflects the actual project, and every subsequent session benefits. This is an intentional trade.**

Before writing any files, gather these facts and keep them in working memory (you'll write them into the scaffold's instruction files and `decisions.md` log).

### Read narrowly, not exhaustively

You're producing a one-page mental model, not a code review. Use line ranges, grep, and directory listings — don't read entire files unless they're short and central.

### What to inspect (in this order)

**1. Repository shape** (~30 seconds of tool calls)

```bash
# top-level layout
ls -la
# detect monorepo or single-package
ls -la apps/ packages/ services/ workspaces/ 2>/dev/null
cat pnpm-workspace.yaml turbo.json nx.json lerna.json 2>/dev/null
# git context
git log --oneline -10 2>/dev/null
git remote -v 2>/dev/null
```

Record: monorepo vs single-package, remote host (GitHub/GitLab/etc.), default branch, rough age of repo (recent commits or long-running?).

**2. Language and runtime**

```bash
ls package.json pyproject.toml requirements*.txt Cargo.toml go.mod Gemfile composer.json pom.xml build.gradle* 2>/dev/null
# version pins
cat .nvmrc .node-version .python-version .ruby-version .tool-versions 2>/dev/null
```

If `package.json` exists, view its first 50 lines. If `pyproject.toml` exists, view it. Record: primary language(s), version, package manager.

**3. Frameworks and libraries**

For JS/TS:
```bash
grep -E '"(next|nuxt|remix|astro|svelte|react|vue|express|fastify|hono|nest|trpc)"' package.json
grep -E '"(prisma|drizzle|sequelize|typeorm|kysely)"' package.json
grep -E '"(vitest|jest|mocha|playwright|cypress)"' package.json
```

For Python:
```bash
grep -E "(django|fastapi|flask|starlette|pydantic|sqlalchemy|alembic|pytest)" pyproject.toml requirements*.txt 2>/dev/null
```

For Go / Rust / etc., scan `go.mod` / `Cargo.toml` for major dependencies.

Record: web framework, ORM/data layer, test framework, anything else load-bearing.

**4. Conventions already in the codebase**

```bash
# linting / formatting
ls .eslintrc* .prettierrc* biome.json ruff.toml .editorconfig 2>/dev/null
# CI / deploy
ls .github/workflows/ .gitlab-ci.yml fly.toml vercel.json netlify.toml Dockerfile docker-compose.* 2>/dev/null
# secrets / env
ls .env.example .env.sample 2>/dev/null
# pre-existing AI configs (might conflict with what you're about to write)
ls AGENTS.md CLAUDE.md GEMINI.md JULES.md CONVENTIONS.md \
   .cursorrules .windsurfrules .clinerules* 2>/dev/null
ls .claude .cursor .windsurf .roo .kilocode .codex .gemini .agents 2>/dev/null
ls .specify 2>/dev/null
```

Record: linter, formatter, CI provider, deployment target, **any existing AI config that already exists** (you must not blindly overwrite it — see step 6 below).

**5. Code patterns** (sample, don't catalog)

```bash
# how does the project organize source?
ls src/ app/ lib/ pkg/ internal/ 2>/dev/null
# how do they name things? grab a few examples
find src -type f \( -name "*.ts" -o -name "*.tsx" -o -name "*.py" -o -name "*.go" \) 2>/dev/null | head -20
```

View 2–3 representative files (handlers, models, tests) for **20–30 lines each**, just to absorb the local style. Record: file naming (kebab/camel/snake), export style (default vs named), test placement (colocated vs separate `tests/` dir).

**6. Existing AI configs — handle with care**

If any of these already exist:
- `AGENTS.md` with content (not just a stub)
- `CLAUDE.md`, `GEMINI.md`, `.cursorrules`, `.clinerules*`, `.windsurfrules`
- `.claude/`, `.cursor/`, `.windsurf/`, `.roo/`, `.kilocode/`, `.codex/`, `.gemini/`, `.agents/`, `.specify/`

…the agent has been set up before. **Do not overwrite.** Options, in order of preference:
1. **Merge**: read what's there, identify gaps, only write the files that are missing.
2. **Augment**: add a new file (e.g., `CLAUDE.local.md` or a new rule file) rather than rewriting the existing one.
3. **Ask**: surface the conflict to the user and ask whether to merge, replace, or skip.

### What to record (becomes scaffold inputs)

After the inspection, you should be able to fill in this mental form. Keep it as a draft for the decisions log:

```
Project: <name>
Type: <monorepo | single-package | library | service | CLI | full-stack>
Primary language: <ts | py | go | rs | etc> (<version>)
Package manager: <npm | pnpm | uv | cargo | etc>
Framework: <next | fastapi | gin | etc | none>
Data layer: <prisma | sqlalchemy | raw SQL | none>
Tests: <vitest | pytest | go test | etc>      Command: <`pnpm test` | `pytest -q` | etc>
Lint:  <eslint | ruff | none>                 Command: <`pnpm lint` | etc>
CI: <github-actions | gitlab-ci | none>
Deploy: <vercel | fly | k8s | container | bare-metal | none>
Conventions: <kebab-case files, named exports, colocated tests, etc>
Existing AI config: <none | CLAUDE.md | .cursor/rules/ | other — and how you handled it>
Anything weird: <one-line gotchas — "API client never throws", "vendor/ never modified", etc>
```

### How this feeds the scaffold

- **Fill the `<stack>` placeholders** in the instruction files (CLAUDE.md, AGENTS.md, .cursor/rules/00-core.mdc, etc.) with what you found — *not* with the boilerplate `<populate>`.
- **Drop topical files that don't apply.** No database in this repo? Skip `data.md`/`data.instructions.md`. No deployment target? Skip `deployment.md`.
- **Pick MCPs based on findings.** GitHub remote → enable `github`. Postgres detected → consider `postgres`. No DB → just filesystem + git + web-search.
- **Seed the decisions log** with the form above as the first entry.

This is the analysis step. Now proceed to profile the user, identify yourself, then run the skills discovery step below.

## Step 0b — User profiling (interactive, first run only)

> **This step personalizes the scaffold.** Two developers on the same repo might need different agent behavior: a junior wants more guidance; a senior wants autonomy. A spec-first developer wants the agent to push back on "just do it"; a code-first developer wants to skip ceremony. This step captures that.

### When to run

- **First initialization:** always ask.
- **Profile already exists** (in `.agents/instructions/project-context.md` or the platform's main instruction file): skip, unless the user explicitly says "update my profile".
- **Autopilot / can't interact:** use sensible defaults (senior, high autonomy, balanced strictness, code-first). Note in the report that the profile is defaulted and can be customized.

### Questions to ask (in this order)

Ask these one by one. Don't dump all questions at once. Adapt phrasing to be natural.

1. **Role and experience level:**
   *"What's your role and experience level? (e.g., senior full-stack, junior frontend, solo founder, tech lead)"*

2. **Primary expertise:**
   *"What frameworks/tools are you most experienced with? (e.g., React + Next.js + PostgreSQL, or Django + AWS, etc.)"*

3. **Working style:**
   *"When building something non-trivial, do you prefer to spec it out first, or jump into code and iterate?"*
   → Maps to: spec-first | code-first | mixed

4. **Autonomy:**
   *"How much should I confirm before acting? Some developers want me to just do obvious things; others prefer I check first."*
   → Maps to: high | medium | low

5. **Review strictness:**
   *"When reviewing code, should I flag everything (style, naming, docs) or only real problems (bugs, security, logic)?"*
   → Maps to: strict | balanced | relaxed

6. **Communication style:**
   *"Do you prefer concise responses (just the answer) or detailed explanations?"*
   → Maps to: concise | detailed | match-my-style

7. **Any preferences I should know about?** (open-ended)
   *"Anything else — coding conventions you like, patterns you avoid, pet peeves?"*

### Where the profile lives

- **Single-agent setup:** embed directly in the platform's main instruction file (CLAUDE.md, copilot-instructions.md, AGENTS.md, etc.) as the Block A.0 section.
- **Multi-agent setup:** put in `.agents/instructions/project-context.md` and reference from each platform's entry file.

### Profile affects the entire scaffold

The answers you get here influence:
- **Block A.2 (Working principles):** autonomy level adjusts which principles say "confirm" vs "just do it"
- **Block A.6 (Dispatch rules):** review chaining behavior adapts to strictness preference
- **Reviewer agent:** strictness level determines what severity of findings to surface
- **Workflow selection:** spec-first users are nudged toward `/speckit.specify`; code-first users skip to implementation
- **Response tone:** concise users get terse answers; detailed users get explanations

## Step 1 — Skills discovery (universal, every agent does this after Step 0)

> **This step is mandatory.** After analyzing the project (Step 0) and identifying yourself, you must go through this skills discovery process before creating the scaffold. `find-skills` is installed automatically; the interactive part is presenting each discovered skill to the user one by one.

### 1a. Install find-skills automatically

The `find-skills` meta-skill (from `vercel-labs/skills`) is a prerequisite for skill discovery. **Install it automatically — do not ask the user for permission.** This is infrastructure, not a choice:

```bash
npx skills add vercel-labs/skills --skill find-skills -a <your-agent> -y
```

This is a non-negotiable first step. If the install fails (e.g., `npx` not available), tell the user what went wrong and how to fix it, then continue with scaffold creation using only hand-written skills.

Agent flags for the install command:

| Agent | `-a` flag |
|---|---|
| Claude Code | `claude-code` |
| Cursor | `cursor` |
| Codex CLI | `codex` |
| Cline | `cline` |
| Windsurf | `windsurf` |
| GitHub Copilot | `github-copilot` |
| Gemini CLI | `gemini-cli` |
| Roo Code / Kilo Code / Others | omit `-a` or check `npx skills add --help` |

### 1b. Run the mandatory search matrix

> **Don't free-form your searches.** Agents kept missing categories — UI/UX skills on frontend projects, Azure skills on Azure projects, etc. — because they ran 2–3 narrow queries and stopped. To prevent that, every Step 0 signal triggers a fixed set of `npx skills find` queries. Run every applicable row below before moving on.

| Step 0 signal | Mandatory search queries |
|---|---|
| **Universal — always run** | `code-review`, `testing`, `git`, `documentation`, `refactoring`, `debugging` |
| Frontend framework (React/Vue/Svelte/Angular/Next/Nuxt/Remix/Astro/etc.) | `<framework>`, `frontend`, `ui`, `ux`, `design`, `accessibility`, `components`, `tailwind` (if detected), `css` |
| Backend framework (Express/Fastify/Hono/Nest/FastAPI/Django/Flask/Rails/Gin/Echo/etc.) | `<framework>`, `<language>`, `api`, `backend`, `rest`, `graphql` (if schema detected) |
| Database / ORM (Prisma/Drizzle/SQLAlchemy/TypeORM/Alembic/etc.) | `<orm>`, `<db-engine>`, `database`, `migrations`, `sql` |
| Cloud — Azure (`@azure/*`, Bicep, App Service, CosmosDB, etc.) | `azure`, `cloud`, `infrastructure` + specific services found (e.g., `cosmosdb`, `cognitive-services`) |
| Cloud — AWS (`aws-sdk`, CDK, CloudFormation, S3, Lambda, etc.) | `aws`, `cloud`, `infrastructure` + specific services found |
| Cloud — GCP (`@google-cloud/*`, Cloud Run, Firestore, etc.) | `gcp`, `google-cloud`, `cloud` + specific services found |
| IaC (Terraform/Pulumi/Bicep/CloudFormation/CDK) | `<tool>`, `iac`, `infrastructure-as-code`, `infrastructure` |
| Containers / orchestration (Docker/Compose/Kubernetes/Helm) | `docker`, `kubernetes`, `containers`, `devops`, `helm` (if detected) |
| CI/CD (GH Actions/GitLab/Jenkins/CircleCI/Azure Pipelines) | `<platform>`, `ci`, `cd`, `pipelines`, `deployment` |
| Testing (Vitest/Jest/Mocha/Pytest/Playwright/Cypress/etc.) | `<framework>`, `testing`, `qa`, `e2e` (if detected), `coverage` |
| Auth / security (OAuth/JWT/NextAuth/Auth0/Clerk/secret managers) | `auth`, `security`, `oauth`, `jwt`, `secrets` |
| Mobile (React Native/Expo/Flutter/SwiftUI/Capacitor) | `<framework>`, `mobile`, `ios`, `android` |
| AI / ML (PyTorch/TensorFlow/transformers/LangChain/AI SDKs) | `<framework>`, `ai`, `ml`, `llm`, `prompt-engineering` |
| Documentation tools (Docusaurus/MkDocs/Storybook/TypeDoc) | `<tool>`, `documentation`, `docs`, `technical-writing` |
| Monorepo (Turborepo/Nx/Lerna/pnpm workspaces) | `<tool>`, `monorepo`, `workspaces` |
| Observability (Datadog/Sentry/Prometheus/OpenTelemetry/Grafana) | `<tool>`, `observability`, `monitoring`, `logging`, `tracing` |

**Coverage rule.** If Step 0 detected a signal, the corresponding row's queries are non-optional. A row can be short-circuited only after running it and finding zero relevant candidates — and that fact must be logged in the coverage report (Step 1d).

**Browse skills.sh.** When CLI results look thin for a detected signal, also browse <https://skills.sh/> — some skills aren't fully indexed in the CLI.

### 1c. Present each candidate and ask — one by one

For every skill returned by the matrix that looks relevant to this project:

1. **Name** the skill and its source repo.
2. **Explain** in one sentence what it does.
3. **Mention install count** if visible (1K+ = safe bet; under 100 = flag this to the user).
4. **Ask**: *"Would you like me to install `<skill-name>`?"*
5. If yes → run `npx skills add <owner/repo> --skill <name> -a <agent> -y`
6. If no → skip; note the reason in the coverage report (Step 1d).

**Present every candidate ≥100 installs. Don't pre-filter.** The user is the filter, not the agent. The previous "strongest 2–3 per category" rule kept strong skills (`frontend-design`, `ui-ux-pro-max`, `azure-enterprise-infra-planner`, etc.) from ever surfacing — don't repeat that mistake. If 20+ candidates come back for one category, group them with sub-headings, but still list them all.

Surface **<100-install candidates only when a detected category produced nothing else**, and label them explicitly: *"Low install count, but this is the only skill that targets `<X>`. Want it anyway?"*

### Autopilot / non-interactive fallback

Some agents run in autopilot mode where they cannot ask the user questions mid-session (e.g., GitHub Copilot coding agent, or any agent running unattended). **This does not mean you skip skill discovery.** Instead:

1. Install `find-skills` automatically (same as interactive mode).
2. **Run the full search matrix from Step 1b** — every row Step 0 made applicable. No short-cuts.
3. **Install every candidate that scores 1K+ installs and matches the project's stack.** Skip anything under 100 installs or unrelated.
4. In your final report, include the full coverage report from Step 1d, plus a **"Skills installed automatically"** section listing every skill with a one-line explanation.
5. Add: *"These were installed automatically because I couldn't ask you during this session. To remove any you don't want: `npx skills remove <name>`. To discover more: `npx skills find <keyword>`."*

The key principle: **never skip the matrix or the coverage report just because you can't ask.** The interactive one-by-one flow is preferred; the auto-install-and-report flow is the fallback. Both run the matrix, both produce a coverage report.

### 1d. Coverage report (mandatory before Step 2)

Before moving to scaffold creation, post a coverage report so the user (and future sessions) can see what was searched, what was found, and what was skipped. Format:

```
## Skills discovery coverage report

Step 0 signals detected: <one-line summary>
find-skills installed: yes

| Category | Detected? | Queries run | Candidates ≥100 installs | Installed | Skipped (reason) |
|---|---|---|---|---|---|
| Universal | always | code-review, testing, git, ... | <n> | <names> | <names + reason> |
| Frontend | yes (React+Tailwind) | react, frontend, ui, ux, design, accessibility, components | <n> | frontend-design, ui-ux-pro-max | web-design-guidelines (user declined) |
| Cloud — Azure | yes (App Service+CosmosDB) | azure, cloud, infrastructure, cosmosdb | <n> | azure-enterprise-infra-planner | none |
| Database | yes (Prisma+PG) | prisma, postgres, database, migrations, sql | <n> | ... | ... |
| Testing | yes (Vitest) | vitest, testing, qa, coverage | <n> | ... | ... |
| ... | | | | | |
```

**Gaps the report must explicitly call out:**
- Detected category with **zero candidates found** → one line saying so, plus a nudge to check <https://skills.sh/> manually later.
- Detected category whose candidates were **all skipped** → list candidates + one-line reason each so future sessions can revisit.

**Interactive mode:** post the report inline and confirm before continuing. **Autopilot mode:** include the same report in the final report instead.

Only after the coverage report is posted can you proceed to **Step 2 — Team assembly**.

### 1e. Log and proceed

After the discovery round and coverage report:
- Log each installed skill to your platform's `memory/decisions.md`: `YYYY-MM-DD — Installed skill <name> from <owner/repo> for <reason>.`
- Append the coverage report summary (signals detected, totals installed/skipped per category) to `memory/decisions.md` so future sessions don't redo the same search.
- **Commit `skills-lock.json`** — this file is auto-generated by `npx skills` and pins the exact versions/hashes of installed skills. Treat it like a `package-lock.json`: always commit it, never edit by hand, and run `npx skills update` when you want newer versions.
- Also create `how-to-use-skills.sh` at the repo root (see Universal Files section for contents) and `chmod +x` it.
- Proceed to **Step 2 — Team assembly** to build your project-specific agent team.

## Step 2 — Team assembly (universal, every agent does this based on Step 0 findings)

> **Don't limit yourself to 3 generic agents.** Based on your Step 0 analysis, assemble a full SDLC-aligned team of specialized agents tailored to this specific project. The 3 core agents (Researcher, Implementer, Reviewer) are always created; additional specialists are generated dynamically based on what the codebase actually uses.

### Core team (always created)

These three agents are created for every project, regardless of stack. Their definitions are in each agent's section below — use them as-is.

| Agent | Mandate | Writes? |
|---|---|---|
| **Researcher** | Gather, synthesize, cite. ~400 words. | No |
| **Implementer** | Code + narrowest test + diff summary. | Yes |
| **Reviewer** | Find real problems. Severity-labeled. | No |

### Specialist agents (generated dynamically from Step 0 findings)

### How to write each specialist agent

Every specialist agent follows this template. **Adapt the format to your platform** (`.md` for Claude Code sub-agents, `.mdc` for Cursor workflows, JSON for Roo Code modes, `.instructions.md` for Copilot, `SKILL.md` for Codex/Gemini, etc.):

```markdown
---
description: <one-line summary for when to invoke this agent>
tools: [<allowed tools — read-only for advisory agents, full for engineering agents>]
```

### Rules for multi-agent repos

1. **Single source of truth for content.** All canonical blocks live in `.agents/instructions/`. Platform-specific entry files (`CLAUDE.md`, `.cursor/rules/00-core.mdc`, `copilot-instructions.md`) **reference or inline** from there — never maintain parallel copies.

2. **Single decisions log.** Only one `memory/decisions.md` at `.agents/memory/decisions.md`. Platform-specific memory paths symlink or redirect here:
   ```bash
   # For Claude Code:
   ln -sf ../../.agents/memory/decisions.md .claude/memory/decisions.md
   # For Cursor (reference in 00-core.mdc):
   # "Decisions log lives at `.agents/memory/decisions.md`."
   ```

3. **Single skills directory.** `npx skills` installs to `.agents/skills/` regardless of which agent you're targeting. All agents read from here. Don't duplicate skills across `.claude/skills/`, `.cursor/skills/`, etc.

4. **Platform files are thin.** Each platform's config directory contains ONLY:
   - MCP config (format differs per platform)
   - Settings/permissions (platform-specific)
   - Entry-point file that loads the shared content
   - Platform-specific overrides (e.g., Cursor's `globs`, Copilot's `applyTo`)

5. **User profile is shared.** Block A.0 lives in `.agents/instructions/project-context.md` and all agents read it. The "Learned over time" section is appended by whichever agent discovers a preference — all agents benefit.

6. **Avoid conflicts.** Platform-specific files must not contradict each other. If one agent needs a different behavior, document it as a platform note *within* the shared block, not in a separate parallel file.

### When to apply multi-agent coexistence

- **Only when the user actively uses 2+ agents.** Don't pre-create this structure for a single-agent setup.
- **Ask during initialization:** "Do you use other AI coding agents alongside <this one>? If so, I'll create a shared layer."
- **If adding a second agent later:** run `agentinit add <new-agent>` (or manually) — it creates only the thin platform config and wires it to the existing `.agents/` shared layer.

### Incremental re-initialization (when the project evolves)

Over time, projects add databases, switch cloud providers, adopt new frameworks. When this happens, the scaffold needs updating — but **not a full re-run.** Instead:

1. **Re-run Step 0 only.** Detect what's new since the last analysis.
2. **Diff the signals.** Compare new Step 0 findings against the `decisions.md` entry from the original initialization. What's new?
3. **For each new signal:**
   - Run the applicable rows from Step 1b (skills discovery) for the new signal only.
   - Create the specialist agent from Step 2 for the new signal only.
   - Add the relevant topical rule file (e.g., `data.md` if a DB was added).
4. **Update Block A.1** (project context) with the new findings.
5. **Append to `decisions.md`:**
   ```
   ## YYYY-MM-DD — Scaffold updated (incremental)
   Context: Project now uses <new signal>.
   Decision: Added <specialist agent>, installed <new skills>, added <new rule file>.
   ```

**Don't re-create existing files.** Only add what's new. Don't touch user-customized rules, don't re-run skills discovery for categories already covered, don't rebuild the core team.

---
```markdown
# context-hygiene

Use when a session has gone long, you're rereading files, or the user complains about lost context.

## Core rules
1. **Read narrowly.** Use line ranges. Never dump a 2000-line file when 30 lines will do.
2. **Search before reading.** grep with line numbers, then read the range.
3. **Summarize tool output.** Pipe through head/tail/wc/grep. Don't paste 500 lines back.
4. **Don't reread.** If a file is already in context this session, reference it; don't view again.
5. **Delegate noisy work.** Research and exhaustive search go to `.claude/agents/researcher.md`.
6. **Externalize state.** Long-lived facts → `.claude/memory/decisions.md`. Current plan → TODO.
```

```markdown
1. **Time-box** ("30 min to learn whether X handles Y").
```

```markdown
---
# error-recovery

The wrong response to a failure is to "force it through" with `--no-verify`, `rm -rf`, or `reset --hard`. The right response is to understand what failed and fix the underlying issue.

## Diagnose before acting

1. **Read the error literally.** The top of the stack trace or the first non-trace line is usually the real cause.
2. **Locate the source.** Find the file and line. Read the surrounding 20 lines.
3. **Reproduce smaller.** Can you trigger the same error with a one-line repro? If so, that's now your test case.

## Failure types and responses

| Symptom | First thing to check |
|---|---|
| Type error after refactor | A consumer you missed. Grep for the old name/signature. |
| Test fails locally but passed before | Did you run with the same env / db state? Run with `--reporter=verbose`. |
| Test passes locally, fails in CI | Env diff: env vars, fixture order, race conditions, file-watcher artifacts. |
| Hook fails on commit | Read the hook output fully. Lint/type/test — fix the underlying issue, re-stage, re-commit (do NOT amend). |
| Build fails after a dep update | Check that dep's CHANGELOG. Pin back if unrelated to your change. |
| Migration fails | Don't retry blindly. Check current schema state vs what the migration expects. |
| `git` reports "your branch diverged" | Don't `reset --hard`. Fetch, inspect, rebase or merge intentionally. |
| File is "locked" / `EBUSY` | A watcher (dev server, test runner) holds it. Stop the watcher. Don't `chmod`. |

## Hard "don'ts"

- **No `--no-verify`** to skip a failing hook.
- **No `git reset --hard`** past committed work without confirming.
- **No `rm -rf` on directories you didn't create** in this session.
- **No "fix"** that involves disabling tests, lints, or type-checking unless you're separately tracking the disabled item.
- **No retry-loop** on a failing command. If it failed once, the second run will fail too unless something changed.

## When to escalate

- Pre-existing failure unrelated to your change → tell the user, ask whether to fix or to ignore.
- Destructive recovery would be required → confirm first.
- You don't recognize the state of the working tree (mystery files, unknown branch) → stop, summarize, ask.
```

#### Block A.2 — Working principles

```markdown
## Working principles

1. **Read before you write.** Match existing patterns in this repo. Don't import a pattern from another codebase that doesn't already live here.
2. **Smallest viable change.** Don't refactor as a side effect. Don't add abstractions for hypothetical futures.
3. **One concern per change.** If scope drifts, stop and either confirm with the user or open a separate change.
4. **Surface dependencies.** New packages, env vars, configs, services — flag them before adding.
5. **Match existing test framework.** Don't introduce a second; extend the first.
6. **Trust internal code.** Only validate at system boundaries (user input, external APIs). Don't add defensive checks against your own callers.
7. **No comments unless WHY is non-obvious.** Don't narrate what the code does — names already do that. Don't reference tasks/PRs/issues in comments.
8. **Stop on real ambiguity.** Return one focused question rather than guessing when guessing wrong costs >5 min.
9. **Reversible vs. irreversible.** Local file edits = freely. Pushes / deletes / shared-state changes = confirm first unless the user pre-authorized.
10. **Report what changed, not what you considered.** Final summary is one or two sentences. The diff speaks for itself.
```

#### Block A.4 — Development workflows

```markdown
## Development workflows

Pick the workflow that matches the work. If unsure, ask before starting.

### Feature work (non-trivial)

1. **Spec.** For any feature spanning >1 file or with unclear requirements, draft a short spec first (problem, goals, non-goals, design sketch, acceptance criteria). If Spec-Kit is available, use `/speckit.specify`.
2. **Plan.** List the files you'll touch and the order. If >5 files, get the plan reviewed before coding.
3. **Implement in slices.** Each slice = one logical change + its smallest verifying test. Don't pile multiple slices into one diff.
4. **Test as you go.** Run the test suite for affected files between slices, not just at the end.
5. **Self-review.** Re-read the diff before declaring done. Look for: leftover debug prints, commented-out code, untested branches, unrelated changes.
6. **PR.** Concise title, body explains the why; reference any spec/issue.

### Bug fix

1. **Reproduce first.** Write a failing test (or a precise repro recipe) before touching the fix.
2. **Isolate the cause.** Don't change behavior beyond what the bug requires. If the surrounding code is also broken, note it — fix separately.
3. **Fix.** Smallest change that makes the test pass.
4. **Regression test.** The failing test stays in the suite.
5. **Verify.** Run the affected test file + a quick sanity pass on neighbors.
6. **PR.** Title includes "fix:"; body has repro steps and the test name.

### Refactor (no behavior change)

1. **State the invariant.** "Behavior of X is unchanged" — explicit in the PR.
2. **Verify with tests.** Existing tests must cover the surface. If they don't, add tests before refactoring.
3. **One axis at a time.** Don't rename + restructure + relocate in the same change.
4. **Watch the diff size.** Big mechanical changes deserve their own PR; logic changes deserve their own PR.

### Debug session

1. **Read the error literally.** Stack trace top frame is usually the truth.
2. **Form a hypothesis before changing anything.** Write it down (one sentence).
3. **Make one change at a time.** If 3 things change and the bug goes away, you don't know which fixed it.
4. **If stuck after 20 min**, summarize what you tried and escalate to the user or a sub-agent.
5. **Log the root cause.** When fixed, append a one-line note to `memory/decisions.md` if it's non-obvious.

### Spike / exploration

1. **Time-box.** State the box ("30 min to learn whether library X handles case Y").
2. **No commits in main branches.** Spike on a throwaway branch or scratch dir.
3. **Output is a memo, not code.** End the spike by writing what you learned, not by merging the experiment.
```

#### Block A.6 — Sub-agent dispatch rules

```markdown
## Sub-agent dispatch

Dispatch to a sub-agent (Task tool, /mode switch, or platform equivalent) when:

| Situation | Dispatch to |
|---|---|
| Need to gather facts from >3 files or unfamiliar parts of the codebase | **Researcher** |
| Need to evaluate a library / pattern / migration trade-off | **Researcher** |
| Coding task with clear acceptance criteria and bounded scope | **Implementer** |
| Want a second pass on a diff before declaring done | **Reviewer** |
| Touching schema / migrations | **Database Engineer** (if assembled) |
| Touching CI / Dockerfile / k8s manifests | **DevOps Engineer** (if assembled) |
| Touching auth / crypto / secrets | **Security Engineer** (if assembled) |
| Touching UI / accessibility / design system | **Frontend Engineer** (if assembled) |
| Touching API contracts / schemas | **API Engineer** (if assembled) |
| Touching IaC / terraform / cloud resources | **Cloud Infrastructure Engineer** (if assembled) |
| Touching test strategy / coverage / QA | **QA Engineer** (if assembled) |

**Dispatch contract (what you give the sub-agent):**
1. The goal in one sentence.
2. Relevant files / paths / line ranges already known.
3. What's been ruled out.
4. The output shape you expect (Researcher returns findings; Implementer returns code+test+diff; Reviewer returns severity-labeled list).

**Don't dispatch when:** the task is a single-file edit you can finish in 2 minutes, or when the sub-agent would just redo what you already did. Dispatch is for parallelism and context isolation, not ceremony.

**Chaining protocol (multi-agent handoff):**
When work needs to flow through multiple specialists:
1. Researcher → Implementer: researcher findings become implementer's "pointers" input.
2. Implementer → Reviewer: implementer's diff becomes reviewer's input (auto-chain this for any change >50 LOC or touching security/data paths).
3. Specialist → Implementer: specialist advisory output (e.g., DB Engineer's schema design) becomes implementer's acceptance criteria.
4. Any agent → Security Engineer: auto-trigger security review for any change touching auth/*, middleware/*, or adding new dependencies.

**Adapt to user profile:**
- If user autonomy = high: chain Implementer → Reviewer automatically without asking.
- If user autonomy = low: ask before dispatching to any specialist.
- If review strictness = strict: always chain Reviewer after Implementer, even for small changes.
```

#### Block A.10 — Tool use rules

```markdown
## Tool use rules

**File reads.** Use the platform's read tool with line ranges when possible. Don't dump 2000-line files when 30 lines will do. Search first (grep, ripgrep), then read the matched range.

**Bash / shell.**
- Prefer dedicated tools (read/edit/write) over shell commands for file ops.
- Quote paths with spaces.
- Avoid `cd <project root>` chained to other commands — use absolute paths or run from the repo root.
- Avoid `sleep` loops; use the platform's background/poll mechanisms.

**Editing.**
- Read a file before editing it. Match existing indentation (tabs vs spaces) exactly.
- Prefer a small, targeted edit over a full-file rewrite.

**Long-running tasks.** Run them in the background if your platform supports it; don't block the conversation on a 5-min build.

**Network.** Use the project's existing HTTP client / SDK rather than introducing a new one for a one-off call.

**Secrets.** Never commit `.env`, credentials, tokens. If a `.env.example` exists, mirror its keys but never its values.
```

#### Block A.11 — Error handling and escalation

```markdown
## Error handling and escalation

**Errors you handle silently:**
- Hook failures → fix the underlying issue (lint, type, test), re-stage, retry.
- Transient network errors on first try → retry once with a short delay.
- Permission denied on a file write you expect to own → check path; correct if wrong; don't `chmod` your way around it.

**Errors you escalate immediately to the user:**
- Test suite has a pre-existing failure unrelated to your change.
- Git operation that would lose committed work (`reset --hard`, force-push to shared branch).
- Discovery of secrets in source / history.
- A migration that's irreversible or affects production data.
- Any state that suggests the working tree was modified by something outside this session (mystery files, unexpected branch, unfamiliar staged changes).

**How to escalate:** Stop the current action. Summarize: *what you were trying to do, what you observed, what you'd do next if approved.* One focused question, not a menu of 5.

**Don't:**
- `--no-verify` a hook to "make it pass".
- Delete files you don't recognize to "clean up".
- Reset / discard changes you didn't make to "get back to a clean state".
```

### Skills tooling: `npx skills` and `how-to-use-skills.sh` (universal)

The **`npx skills`** CLI (from `vercel-labs/skills`) is the package manager for the open agent skills ecosystem. It installs `SKILL.md` packages into the right folder for whichever agent(s) you have installed — and it knows about 50+ agents including all the ones in this file.

**Don't hand-roll a "find skills" meta-skill anymore.** There's already an official one called `find-skills` from `vercel-labs/skills`. Install it first, and it teaches the agent how to search the leaderboard, evaluate install counts, and install new skills safely.

**Always create `how-to-use-skills.sh` at the repo root** for both supported and unsupported agents. It's the single source of truth for skill-management commands — both humans and agents look here when they need to remember the syntax.

**`how-to-use-skills.sh`** (place at repo root, mark executable: `chmod +x how-to-use-skills.sh`)
```bash
#!/usr/bin/env bash
# how-to-use-skills.sh — Reference for the npx skills CLI.
#
# This file is documentation, not an installer. It shows the commands
# both humans and AI agents should use to manage skills in this repo.
#
# CLI: https://github.com/vercel-labs/skills
# Directory of skills: https://skills.sh/
# Spec: https://agentskills.io/specification
#
# Run `bash how-to-use-skills.sh help` to print this help.

set -euo pipefail

cmd="${1:-help}"

case "$cmd" in
  help|--help|-h)
    cat <<'EOF'
npx skills — quick reference

INSTALL FROM A REPO (most common)
  npx skills add <owner/repo>                 # all skills from a repo
  npx skills add <owner/repo> --skill <name>  # one specific skill
  npx skills add <owner/repo> --list          # list without installing

  npx skills add https://github.com/<owner/repo>           # full URL works too
  npx skills add ./my-local-skills                         # local path

  -g, --global         install to ~/<agent>/skills/ instead of project
  -a, --agent <name>   target specific agents (claude-code, cursor, codex, …)
  -y, --yes            non-interactive (skip prompts)
  --copy               copy files instead of symlinking
  --all                install all skills to all agents, no prompts

DISCOVER
  npx skills find                  # interactive fzf-style search
  npx skills find <keyword>        # search by keyword
  # Or browse the leaderboard at https://skills.sh/

LIST INSTALLED
  npx skills list                  # project + global
  npx skills ls -g                 # global only
  npx skills ls -a claude-code     # filter by agent

UPDATE
  npx skills update                # all skills, interactive scope
  npx skills update <name>         # one skill
  npx skills update -y             # auto-detect scope, non-interactive

REMOVE
  npx skills remove                # interactive
  npx skills remove <name>         # by name
  npx skills remove --all          # nuke everything (with confirmation)

CREATE
  npx skills init <name>           # scaffold a new SKILL.md

RECOMMENDED FIRST INSTALL
  Install the `find-skills` meta-skill so the agent can discover more later:
    npx skills add vercel-labs/skills --skill find-skills

  Then browse the leaderboard at https://skills.sh and install what fits.
  Skills with 1K+ installs are generally safe bets; under 100, review the
  source before installing.

EOF
    ;;

  bootstrap)
    # One-shot setup: install the find-skills meta-skill so the agent can
    # discover and install further skills on demand.
    echo "Installing find-skills (the meta-skill for discovery)..."
    npx skills add vercel-labs/skills --skill find-skills -y
    echo
    echo "Done. The agent can now run \`npx skills find <query>\` or"
    echo "browse https://skills.sh to find more skills to install."
    ;;

  find)
    shift
    npx skills find "$@"
    ;;

  list|ls)
    shift
    npx skills list "$@"
    ;;

  *)
    echo "Unknown subcommand: $cmd"
    echo "Run \`bash how-to-use-skills.sh help\` for the reference."
    exit 1
    ;;
esac
```

**Agent guidance for using this file:**

1. When you need a capability you don't have, **first check whether `find-skills` is installed** (`ls .claude/skills/find-skills/ 2>/dev/null` or the platform equivalent). If not, install it: `npx skills add vercel-labs/skills --skill find-skills -y`.
2. Then run `npx skills find <query>` or browse <https://skills.sh> to locate the right skill.
3. Install it scoped to the project: `npx skills add <owner/repo> --skill <name>`.
4. Append a one-line entry to your platform's `memory/decisions.md`: `YYYY-MM-DD — Installed skill <name> from <owner/repo> for <reason>.`

Don't manually copy SKILL.md files between directories — let the CLI handle the symlinks. That way `npx skills update` actually works.

### Token-saving rules of thumb

1. **Read narrowly.** Line ranges, not whole files.
2. **Search first.** grep → narrow reads. A search hit is ~10× cheaper than a full file.
3. **Summarize tool output.** Pipe through head/tail/wc/grep before reading.
4. **Don't reread.** Already in context = don't view again.
5. **Lazy-load topic context.** `security.md` for a UI task wastes tokens.
6. **Delegate noisy work.** Research / exhaustive search go to a sub-agent or workflow.
7. **Externalize state.** Long-lived facts → memory. Don't repeat the same summary across turns.

### When to start fresh

- Task has materially changed; old context is stale.
- More time managing the conversation than doing the work.
- Hitting platform limits (rate limits, long-context degradation).

Before fresh-starting: write key decisions and current plan to memory so the next session boots cheap.
