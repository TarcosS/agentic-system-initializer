## Working principles

1. **Read before you write.** Match existing patterns in this repo. Don't import a pattern from another codebase that doesn't already live here.
2. **Smallest viable change.** Don't refactor as a side effect. Don't add abstractions for hypothetical futures.
3. **One concern per change.** If scope drifts, stop and either confirm with the user or open a separate change.
4. **Surface dependencies.** New packages, env vars, configs, services — flag them before adding.
5. **Match existing test framework.** None is configured here; if introducing tests, propose Vitest (Next.js-friendly, fast) before installing.
6. **Trust internal code.** Only validate at system boundaries (user input, external APIs). Don't add defensive checks against your own callers.
7. **No comments unless WHY is non-obvious.** Don't narrate what the code does — names already do that. Don't reference tasks/PRs/issues in comments.
8. **Stop on real ambiguity.** Return one focused question rather than guessing when guessing wrong costs >5 min.
9. **Reversible vs. irreversible.** Local file edits = freely. Pushes / deletes / shared-state changes = confirm first unless the user pre-authorized.
10. **Report what changed, not what you considered.** Final summary is one or two sentences. The diff speaks for itself.

## Development workflows

Pick the workflow that matches the work. If unsure, ask before starting.

### Feature work (non-trivial)

1. **Spec.** For any feature spanning >1 file or with unclear requirements, draft a short spec first (problem, goals, non-goals, design sketch, acceptance criteria). Use `/speckit.specify` when available.
2. **Plan.** List the files you'll touch and the order. If >5 files, get the plan reviewed before coding.
3. **Implement in slices.** Each slice = one logical change + its smallest verifying check (type-check + lint + visual smoke test in `npm run dev`). Don't pile slices into one diff.
4. **Verify as you go.** Run type-check + lint between slices. Open the app in a browser for any UI change.
5. **Self-review.** Re-read the diff before declaring done. Look for leftover debug prints, commented-out code, untested branches, unrelated changes.
6. **PR.** Concise title, body explains the why; reference any spec/issue.

### Bug fix

1. **Reproduce first.** Capture a precise repro (URL, click path, expected vs actual). Add a regression test if a test framework gets introduced later.
2. **Isolate the cause.** Don't change behavior beyond what the bug requires. If surrounding code is also broken, note it — fix separately.
3. **Fix.** Smallest change that resolves the repro.
4. **Verify.** Repro path passes; neighbors still render.
5. **PR.** Title includes `fix:`; body has repro steps.

### Refactor (no behavior change)

1. **State the invariant.** "Behavior of X is unchanged" — explicit in the PR.
2. **Verify with type-check + lint + visual smoke.** No tests yet means visual verification is mandatory.
3. **One axis at a time.** Don't rename + restructure + relocate in the same change.
4. **Watch the diff size.** Big mechanical changes deserve their own PR; logic changes deserve their own PR.

### Debug session

1. **Read the error literally.** Next.js error overlay top frame is usually the truth; check the terminal too.
2. **Form a hypothesis before changing anything.** Write it down (one sentence).
3. **Make one change at a time.** If 3 things change and the bug goes away, you don't know which fixed it.
4. **If stuck after 20 min**, summarize what you tried and escalate to the user or a sub-agent.
5. **Log the root cause.** When fixed, append a one-line note to `.claude/memory/decisions.md` if non-obvious.

### Spike / exploration

1. **Time-box.** State the box ("30 min to learn whether library X handles case Y").
2. **No commits in main branches.** Spike on a throwaway branch or scratch dir.
3. **Output is a memo, not code.** End the spike by writing what you learned, not by merging the experiment.

## Sub-agent dispatch

Dispatch to a sub-agent (Task tool with `subagent_type=<agent name>`) when:

| Situation | Dispatch to |
|---|---|
| Need to gather facts from >3 files or unfamiliar parts of the codebase | **researcher** |
| Need to evaluate a library / pattern / migration trade-off | **researcher** |
| Coding task with clear acceptance criteria and bounded scope | **implementer** |
| Want a second pass on a diff before declaring done | **reviewer** |

**Dispatch contract (what you give the sub-agent):**
1. The goal in one sentence.
2. Relevant files / paths / line ranges already known.
3. What's been ruled out.
4. The output shape you expect (researcher returns findings; implementer returns code + diff; reviewer returns severity-labeled list).

**Don't dispatch when:** the task is a single-file edit you can finish in 2 minutes, or when the sub-agent would just redo what you already did. Dispatch is for parallelism and context isolation, not ceremony.

**Chaining protocol:**
- researcher → implementer: researcher findings become implementer's "pointers" input.
- implementer → reviewer: auto-chain for any change >50 LOC or touching auth / data / config paths.
- Any agent → reviewer: auto-trigger security review for any change adding new dependencies.

**Adapt to user profile (medium autonomy + balanced review):**
- Confirm before dispatching specialists for new architectural directions.
- Auto-chain implementer → reviewer for >50 LOC diffs without asking.
- Skip reviewer for trivial one-liners.

### Claude Code dispatch specifics
- Dispatch via the **Task tool** with `subagent_type=<agent name>` and a self-contained prompt (the sub-agent has no view of the parent thread).

## Git and PR flow

**Branching.** Branch off `main` for every change. Naming: `kebab-case/<type>/<short-desc>` (e.g., `feat/checkout-button`, `fix/layout-overflow`).

**Commits.**
- One logical change per commit. Squash mechanical noise (formatter output, generated files).
- Message style: Conventional Commits — `feat:`, `fix:`, `chore:`, `refactor:`, `docs:`, `test:`.
- Body explains the *why* when non-obvious; the diff explains the *what*.
- Never `--no-verify` unless the user explicitly asks.

**Before pushing.**
1. `npx tsc --noEmit` clean
2. `npm run lint` clean
3. `npm run build` succeeds
4. Re-read the diff one final time

**Pull requests.**
- Title <= 70 chars, declarative.
- Body sections: `## Summary` (2-4 bullets) / `## Test plan` (checklist — manual until tests exist) / `## Risks` (one line) / `## Links` (specs, issues).
- Draft PR is fine for in-progress work; mark ready only when local build is green.
- Self-review the diff in the PR view before requesting reviewers.

**Destructive operations require confirmation:** force-push, branch deletion on shared branches, `git reset --hard` past committed work. Don't do these without explicit user approval, even if the user previously approved a similar action.

## Tool use rules

**File reads.** Use `Read` with `offset`/`limit` for large files. Search first with `Grep`, then read the matched range. Don't dump 2000-line files.

**Bash / shell.**
- Prefer `Read`/`Edit`/`Write`/`Grep`/`Glob` over `cat`/`sed`/`echo`/`find`/`grep`.
- Quote paths with spaces.
- Use absolute paths or run from the repo root; avoid chained `cd`.
- Avoid `sleep` loops; use `run_in_background: true` for long-running tasks.

**Editing.**
- Read a file before editing it (the Edit tool enforces this). Match existing indentation (tabs vs spaces) exactly.
- Prefer small, targeted edits over full-file rewrites.

**Long-running tasks.** Run dev server, builds, watchers with `run_in_background: true`; don't block on them.

**Network.** Use the project's existing fetch / SDK rather than introducing a new HTTP client for a one-off call.

**Secrets.** Never commit `.env*`, credentials, tokens (the `.gitignore` already excludes `.env*`). If a `.env.example` gets added, mirror its keys but never its values.

## Error handling and escalation

**Errors you handle silently:**
- Hook failures → fix the underlying issue (lint, type-check), re-stage, retry.
- Transient network errors on first try → retry once with a short delay.
- Permission denied on a file write you expect to own → check the path; correct if wrong; don't `chmod` your way around it.

**Errors you escalate immediately to the user:**
- Build / lint failure unrelated to the current change.
- Git operation that would lose committed work (`reset --hard`, force-push to shared branch).
- Discovery of secrets in source / history.
- Any state that suggests the working tree was modified outside this session (mystery files, unexpected branch, unfamiliar staged changes).

**How to escalate:** Stop the current action. Summarize: *what you were trying to do, what you observed, what you'd do next if approved.* One focused question, not a menu of 5.

**Don't:**
- `--no-verify` a hook to "make it pass".
- Delete files you don't recognize to "clean up".
- Reset / discard changes you didn't make to "get back to a clean state".
